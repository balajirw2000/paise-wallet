5. CORE BUSINESS REQUIREMENT

Users have wallets containing integer paise. Users can transfer money to each other.

Conservation: Money cannot be lost or created during transfers.

Idempotency: A retry using the same idempotency key must return the original result without moving money again. Same idempotency key + different request body must return 409.

Race-free wallet creation: Concurrent first-time transfers involving new users must create each wallet exactly once, with no duplicate wallet rows and no race-condition-induced 500.

Authorization: A caller can only spend from their own wallet and read transfers in which they are a participant. Caller identity must come exclusively from the verified JWT.

6. MONEY REPRESENTATION

Money must be represented as integer paise using BIGINT / Java long.

Never use float.

Never use double.

Never use floating-point arithmetic for balances.

Database constraints must enforce balance_paise >= 0 and amount_paise > 0.

7. DATABASE SCHEMA

CREATE TABLE wallets (
    user_id TEXT PRIMARY KEY,
    balance_paise BIGINT NOT NULL DEFAULT 0 CHECK (balance_paise >= 0),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE transfers (
    transfer_id UUID PRIMARY KEY,
    from_user TEXT NOT NULL REFERENCES wallets(user_id),
    to_user TEXT NOT NULL REFERENCES wallets(user_id),
    amount_paise BIGINT NOT NULL CHECK (amount_paise > 0),
    idempotency_key TEXT NOT NULL,
    request_hash TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'APPLIED',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_idem UNIQUE (from_user, idempotency_key)
);

CREATE INDEX idx_transfers_to_user
ON transfers(to_user);

Use Flyway for schema creation.

9. TRANSFER VALIDATION

to_user must not equal caller.

amount_paise must be greater than 0.

idempotency_key must be non-blank.

request_hash = SHA-256(to_user + ":" + amount_paise).

Caller identity must come from the verified JWT sub.

10. TRANSFER TRANSACTION — CRITICAL

All transfer logic must happen inside one PostgreSQL transaction using READ COMMITTED.

1. Validate request: to_user != caller; amount_paise > 0; idempotency_key is non-blank.

2. Calculate request hash: SHA-256(to_user + ":" + amount_paise).

3. Begin transaction: Use one database transaction with READ COMMITTED.

4. Get/create wallets: INSERT INTO wallets(user_id) VALUES (?) ON CONFLICT (user_id) DO NOTHING. Never SELECT then INSERT.

5. Lock both wallets: SELECT user_id, balance_paise FROM wallets WHERE user_id IN (?, ?) ORDER BY user_id FOR UPDATE. Always acquire locks in user_id order.

6. Check idempotency: Look up (from_user, idempotency_key). Same hash => replay with no mutation. Different hash => 409.

7. Check balance: If caller balance < amount, reject with 422 and do not mutate balances.

8. Insert transfer: Insert transfer. Handle unique-constraint races by re-reading the existing row, comparing hashes, and returning the stored outcome without moving money twice.

9. Mutate balances: Debit sender and credit recipient inside the same transaction.

10. Commit: Commit only after all operations succeed; return {transfer_id, new_balance}.

11. IDEMPOTENCY REQUIREMENTS

Use UNIQUE (from_user, idempotency_key). Store idempotency_key, request_hash, transfer_id, status, and created_at.

Same caller + same idempotency key + same request body => return original result.

Same caller + same idempotency key + different request body => 409 Conflict.

Never perform the balance mutation twice.

13. AUTHENTICATION

Implement JwtFilter extending OncePerRequestFilter.

Verify HS256 using JWT_SECRET.

Extract sub.

Create a request-scoped CallerContext.

Make caller identity available to application code.

Missing or invalid JWT => 401.

GET /dev/token?user=<id> mints a 1-hour HS256 JWT only when DEV_TOKENS_ENABLED=true.

Public endpoints: /healthz, /readyz, /metrics, and /dev/token when enabled.

Never accept caller identity from request body, headers, or query parameters.

14. OBSERVABILITY

CorrelationIdFilter: read/generate X-Request-Id, put it in MDC, and echo it in the response header.

Structured JSON logs must include request_id and useful event fields.

Log events: transfer.applied, transfer.rejected, insufficient_funds, transfer.idempotent_replay, transfer.conflict, wallet.getorcreate.race_lost, auth.failure.

Micrometer counters: transfers_applied_total and transfers_rejected_total{reason="..."}.

Expose Prometheus metrics at /metrics.

Expose HTTP request metrics including latency information sufficient to observe p50/p95/p99.
